## 背景与决定

维护者要求完整接管 Akashic。只复制 Core 不足以做到这一点：插件 CI、安装默认值、
自部署和 Computer 镜像仍可能依赖原作者的仓库或制品。

本项目的 Core 来源为 `namei32/akashic`，extra 来源为
`namei32/akashic-plugins`。新插件仓库保留上游的源码历史、分支和标签，
`origin` 指向个人仓库，`upstream` 只供主动比较和合入；不自动同步到生产。

沿用两仓结构，因为插件独立构建和更新不需要重新发布 Core。extra 的 `main`
保存源码，CI 从个人 Core 仓库检出 `CORE_REF`，生成 `release/*` 与 `index`；
发布分支继续由内容决定提交，不改成普通开发分支。Core 和 Computer 镜像由个人 CI
发布到 `ghcr.io/namei32/`。继承的镜像摘要在自己的制品发布、验证后再切换。

安装器保留显式 `--origin`、`AKASHIC_INSTALL_ORIGIN` 和 extra 来源覆盖入口。
默认使用个人来源；来源不可用时按既有失败语义报错，不回退到作者仓库。
Shell 自部署采用同一 Core 默认来源。

## 已有实例的切换边界

改变源码默认值不修改正式选择、启停、配置、数据目录或历史。包管理器会按来源匹配
已安装插件，因此必须从 live selection 逐项固定代码提交和来源，经过正式安装链显式
切换；不得直接修改 cache 的 Git remote 来伪装安装，也不能用全量重装覆盖私人插件。

来源切换首先使用已验证的等价代码，沿用插件身份、配置引用与 `data_dir`。本地 bundle、
仅存缓存的源码和私人插件单独核对。旧 Feed 不在 extra 仓库中，其 Watch 接口迁移是
独立功能改动，不能因为 clone 完成就宣称 RSS 已恢复。

失败时保留旧选择和发布证据；若正式发布已提交，按部署手册核对实际选择及业务数据
后恢复。代码指针回退不等于数据迁移回滚。无自动数据清理，也无批量重新启用停用插件。

## 验收

先核对复制前后的 refs，再在隔离环境从个人仓库解析版本、构建和安装。
代码 CI 与插件边界检查应通过；每份证据记录 Core 和 extra 的实际 SHA。
正式部署另行授权，比较运行能力和相关持久数据，并验证业务入口。
普通第三方依赖仍使用其来源；本决定接管的是作者个人仓库与发布资产。
